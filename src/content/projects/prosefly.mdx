Prosefly began with a recurring problem: every documentation project needed the same dependable
shell, but copying a finished site also copied its assumptions. Navigation, search, MDX components,
theme controls, and responsive behavior were useful across projects. A particular layout and brand
were not.

The project turns those recurring pieces into a small Astro ecosystem. Content stays in the
repository as Markdown and MDX, themes provide complete documentation shells, and shared packages
handle the parts that should behave consistently everywhere.

<Callout type="note" title="The product principle">
  Start with considered defaults, then change the parts that matter through
  configuration and semantic tokens.
</Callout>

## A set of tools, not one all-purpose framework

The packages have deliberately narrow responsibilities. This makes it possible to use a complete
theme, adopt only the content components, or add API reference tooling to an existing Astro site.

## Content is the durable layer

The durable part of a documentation site is usually its information architecture, URLs, and
writing. Prosefly therefore builds around Astro content collections instead of moving documents
into a theme-owned database. Schemas validate frontmatter, ordinary Git workflows review changes,
and the same source files can move between themes.

That boundary also keeps the dependency direction understandable. Lotus and Dahlia depend on the
shared component package; the component package does not know about either theme. Astro OpenAPI
produces a normalized content model but leaves routes and page composition to the consuming site.

## The website is part directory, part documentation

The Prosefly site introduces the product family, publishes the shared package documentation, and
points to live theme demos and starter repositories. It is built with Lotus itself, so improvements
to the documentation experience are exercised on the project's own public site.

The result is intentionally modest: a maintained set of interoperable tools rather than a platform
that owns the entire site. A team can begin with a theme, replace its visual system over time, or
keep only the components that continue to earn their place.
